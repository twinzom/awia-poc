AI-Native Wealth Agent: MVP Design

The first version of the wealth agent: one dedicated agent per client, for portfolios of listed equities. It onboards itself, listens to seven signal detectors, tells the client what matters, answers questions, and proposes trades that the client approves.

This document takes what the MVP needs from the overall design and the signal detectors design, cuts it to the equity-only scope, and marks what waits for later. Table names, limits and thresholds are proposed starting values.

Scope

What the MVP has to prove, and where its boundary is.

What the MVP must prove

01 · Zero-instruction

Self-onboarding

The agent works out what to watch from the client's portfolio and history. Nobody configures it.

02 · Personal

One agent per client

Each client has a dedicated agent with its own memory, inbox and outbox.

03 · Selective

Subscribe, don't firehose

It listens only to signals about the client's stocks and markets, and stays silent when nothing matters.

04 · Proactive + on demand

Speaks first, also answers

It alerts and reports without being asked, and answers questions at any time.

05 · Safe

Acts only with approval

It can propose orders, but nothing executes until the client approves the exact order.

Part 2

How it works

The agent is asleep almost all the time. It wakes for a short run when an event arrives, works inside a session, saves what it learned, and goes back to sleep.

From onboarding to action

  1. Understand: the client's first event is onboarding. That run reads the portfolio, profile and history and writes notes/.
  2. Listen: the same run sets the default subscriptions (below) and the weekly digest schedule. It starts on the quietest delivery settings.
  3. Act: when a signal arrives, the agent relates it to the holdings, researches, analyzes, and decides: say nothing, add a finding to the digest, send a report or alert, set a follow-up, or propose an order.
  4. Refresh: new holdings, client questions and the nightly dreaming job keep memory and subscriptions current.

The common contract

Every detector uses the same subscription interface and the same signal format, so the agent learns one way to subscribe and the platform handles every detector the same way. Full detail is in the signal detectors design.

Kinds and params

kinds

Which events?

The types of event to receive. If kinds is left out, the subscription gets the kinds marked default.

params

How big?

Thresholds on the signal's measurements. Each param applies only to the kinds it lists, and a kind with no applicable params always passes.

Agent tools

update_subscriptions(changes: [{
  op:         "add" | "update" | "remove",
  detector:   "price_move",
  topic:      "ticker:NVDA",
  kinds:      ["price_move.*", "trading.*"],     # which events; default = the detector's default kinds
  params:     {"min_z": 2.5, "min_move_pct": 3},   # how big; validated against the catalogue
  expires_at: "2026-12-15",                       # optional; a temporary watch
  reason:     "18% of portfolio"                  # required; goes to the audit log
}])
→ per change: applied | applied_with_warning(reason) | rejected(reason) | blocked(reason)

list_subscriptions(detector?, topic?)
describe_detector(detector)           → kinds and params in full: type, default, floor, applies_to, checks
acknowledge(signal_id, reason)        → for must_acknowledge signals handled without a message

Tables

CREATE TABLE detector_catalog (
  detector_id     text    PRIMARY KEY,       -- 'price_move'
  scope           text    NOT NULL,          -- 'shared' | 'client'
  version         text    NOT NULL,          -- stamped on every signal
  topic_patterns  text[]  NOT NULL,          -- {'ticker:*'}
  kinds           jsonb   NOT NULL,          -- [{kind, on_by_default, default_severity, must_acknowledge, measurements}]
  params          jsonb   NOT NULL,          -- {name: {type, default, floor, applies_to, checks, description}}
  summary         text    NOT NULL           -- rendered into the system prompt
);

CREATE TABLE subscriptions (
  client_id    uuid         NOT NULL,
  detector_id  text         NOT NULL REFERENCES detector_catalog,
  topic        text         NOT NULL,
  kinds        text[],                              -- NULL = the detector's default kinds
  params       jsonb        NOT NULL DEFAULT '{}',
  set_by       text         NOT NULL,               -- 'onboarding' | 'agent' | 'client' | 'system'
  mandatory    boolean      NOT NULL DEFAULT false, -- system rows the agent can't remove
  reason       text         NOT NULL,
  expires_at   timestamptz,
  updated_at   timestamptz  NOT NULL DEFAULT now(),
  PRIMARY KEY (client_id, detector_id, topic)
);
CREATE INDEX ON subscriptions (detector_id, topic);

How the filter matches a signal

for signal in signal_bus:
    subs = subscriptions.where(detector_id = signal.detector, topic IN signal.topics, not expired)
    for client_id, rows in group_by(subs, "client_id"):
        hits = [r for r in rows
                if kind_matches(r.kinds or detector.default_kinds, signal.kind)
                and params_pass(detector, r.params, signal)]   # each param checked only for its kinds
        if not hits:
            continue                                           # dropped: no run, no cost
        inbox.insert(client_id, source="detector", type="signal",
                     source_event_id=signal.signal_id,
                     priority=signal.severity_hint,
                     available_at=batch_time(signal.severity_hint),
                     payload=signal + {"matched": hits})       # one event per client

Client detectors (D1, D6) skip the bus. They check their one client's subscription row in the same way and post to the ingest handler directly.

severity_hint is not the client's priority. It is the size of the fact in the market. The agent decides what it means for this client and sets the message's kind and priority itself.

A1Price move detector

shareddetector_id: price_movestreamingp95 ≤ 5 s

Watches the price of every stock and ETF that at least one client holds or watches, and emits a signal when a move is unusual for that instrument. Unusual is measured in σ, multiples of the instrument's normal daily move, so the same rule works for a stable blue chip and a volatile small cap.

Inputs

  • Exchange quotes and trades: last price, volume, bid/ask
  • Official closing prices
  • Trading status: halts, suspensions, resumptions, limit-up/limit-down
  • Reference data: split and dividend adjustment factors, benchmark and beta, sector and region tags
  • Active universe: instruments with at least one subscriber

How it detects

  • Normalise: adjust the previous close for splits and ex-dividend dates, so a 2-for-1 split doesn't look like a crash. Drop ticks that feed health flags as bad.
  • Baseline: per instrument, an EWMA daily volatility (λ = 0.94, about 60 days) and beta to its benchmark, updated at each close.
  • Detect: for each window, z = return ÷ (σ_daily × √elapsed). Also a residual z after removing beta × the benchmark's move, separating the stock's own move from the market's. Opening gaps and status changes.
  • Debounce: arm at |z| ≥ 2.5, re-arm below 1.5, bands at 4σ and 6σ; one signal per instrument, window, direction and band per day.

A6Market regime detector

shareddetector_id: market_regimestreamingp95 ≤ 5 s

Watches each market as a whole: index shocks, drawdowns from the peak, market-wide circuit breakers and exchange closures. One signal can wake many agents at once. This is the MVP's breaking-event path, where every exposed client gets a personal alert and unexposed clients get nothing.

Inputs

  • Major indices for the MVP markets (e.g. HSI, HSCEI, S&P 500, Nasdaq 100)
  • Exchange status: market-wide circuit breakers, unscheduled closures (such as a typhoon or black-rainstorm warning in Hong Kong), outages
  • Index history: 52-week peaks and volatility
  • Client exposure table, computed nightly: each client's beta to each market, used only to order the fan-out

How it detects

  • Normalise: align sessions and time zones. A US shock overnight shows up as an Asian gap the next morning.
  • Baseline: rolling 52-week peaks for drawdowns; index volatility for z-scores.
  • Detect: index shocks (|z| ≥ 4 intraday); drawdown bands from the peak (−5% pullback, −10% correction, −20% bear market); circuit breakers and closures.
  • Debounce: a drawdown band fires once and re-arms after the index recovers half the band; shocks once per index per day per band.

B1Earnings & guidance detector

shareddetector_id: earningscalendar dailyresults ≤ 2 min

Watches company results: the calendar before each report, the result compared with what analysts expected, and changes to the company's own outlook (guidance). Results days are when single stocks move most. Knowing a report is coming lets the agent prepare the client instead of only reacting afterwards.

Inputs

  • Earnings calendar: confirmed report dates and whether before or after market
  • Consensus estimates: EPS, revenue and key segment figures from an estimates vendor
  • Results releases: press releases and exchange filings, parsed
  • Guidance: the company's own outlook ranges
  • Estimate revisions: daily changes to consensus

How it detects

  • Normalise: map each release to its issuer and fiscal period; compare on the same basis as consensus (adjusted or reported); adjust per-share figures for splits.
  • Baseline: freeze the consensus just before the release; keep the history of past surprises, so a surprise can be expressed in σ.
  • Detect: a pre-event signal for confirmed dates; surprise % = (actual − consensus) ÷ |consensus| for EPS and revenue; guidance raised, cut, withdrawn or started; consensus for next year's EPS moving more than 5% in 30 days.
  • Debounce: one result signal per release; one guidance signal per statement; revision trends at most monthly per issuer.

B3Corporate actions detector

shareddetector_id: corporate_actionscustodian feed every 15 minhas mandatory kinds

Watches things a company does to its securities: dividends, splits, rights issues, tender offers, mergers, bond calls. Some of these are elective: the client must choose an option before a deadline, or a default option is applied that can cost money. The source is the custodian's corporate-action feed, which is authoritative.

Inputs

  • Custodian corporate-action notices: ISO 15022 MT564 or ISO 20022 seev messages, with replacements
  • Issuer announcements: often earlier than the custodian, but unofficial
  • Dividend history per issuer
  • Market calendars: business days for deadlines

How it detects

  • Normalise: map events to ISIN; apply replacement notices; classify as mandatory, voluntary (elective) or mandatory with options.
  • Baseline: the last comparable dividends and the stated policy per issuer.
  • Detect: a new event; a dividend cut, suspension, raise or special dividend compared with the last comparable payment; an election window opening, with options, the default option and the deadline; completion.
  • Debounce: one signal per event per stage; replacement notices update the same story.

shareddetector_id: newsstreamingarticle → inbox p95 ≤ 60 s

Turns the flow of news into stories. It tags each article with the companies, sectors, places and themes it is about, groups articles on the same event into one story, and scores how new and how important the story is. This replaces the tagging the subscription filter did on raw news in the overall design.

Inputs

  • Licensed newswires, real time
  • Regional and local-language news, with headline and summary translated
  • Entity master: company names, brands and people → issuer IDs
  • Source credibility ratings

How it detects

  • Tag: a model recognises the entities in each article and links them to issuers, sectors, regions and themes, once per article.
  • Cluster: group articles about the same event (similar content and shared entities within 48 hours) into a story.
  • Score: novelty (is this a new story?), importance 1–5 (event type × source credibility × how central the entity is), sentiment, and news volume against each entity's normal level.
  • Debounce: one signal per new story; an update only when importance moves up a band or the story adds new facts; syndicated copies are dropped.

D1Concentration detector

clientdetector_id: drifton fills and price signalshourly at most

In an all-equity portfolio, asset-class drift doesn't apply: everything is equity. The main portfolio-level risk is concentration in one stock, sector or country. This detector compares the client's exposures, looking through ETFs, with the bank's limits and any limits specific to the client.

Inputs

  • Positions and valuations from the portfolio system
  • ETF look-through: constituents and their weights
  • Classification: sector and country for every stock
  • Concentration limits: bank policy (e.g. 10% per issuer, 30% per sector) plus any client-specific limits

How it detects

  • Normalise: value every position in the reporting currency.
  • Look through: break ETFs into their constituents, so a direct NVDA holding plus a semiconductor ETF adds up correctly.
  • Detect: an issuer, sector or country above its limit.
  • Debounce: re-arm only when the weight is back 1 point below the limit; signal again if it grows by another 5 points.

D6Account activity detector

clientdetector_id: activityreal timefills ≤ 10 s

Reports what happened in the client's accounts: orders filled, partly filled, rejected or expired; money in and out; instructions received. It turns the overall design's portfolio webhook into proper signals, and it is how the agent learns that an action it got approved has completed.

Inputs

  • Order events: fills, partial fills, rejections, expiries
  • Cash movements: deposits, withdrawals, dividends received
  • Deferral links: order ↔ deferral ↔ session

How it detects

  • Normalise: map every event to account and client.
  • Link: attach the deferral and session that approved an order, so the signal resumes that session.
  • Detect: order state changes; cash movements above a threshold; activity far from the client's normal pattern.
  • Debounce: one signal per state change; partial fills batched per order every 15 minutes.

FFeed health

A wrong signal is worse than no signal. Feed health watches every detector input. Agents don't subscribe to it.

What it checks

  • A heartbeat per input against its expected cadence; the age of the last update
  • Gaps in sequences, and missing closes
  • Bad ticks: a jump over 10σ on tiny volume that reverses within seconds
  • A cross-check of the main indices against a second source

What it does

  • Pauses detection for the affected instruments
  • After recovery, rebuilds the baseline and emits only the current state, not a backlog
  • Sets "market data delayed since 14:05" in the run header, and alerts ops
  • The permission gate's price-drift check before execution stays as a final guard

Status flow: pending → claimed → done. If the worker's lease expires, claimed events go back to pending with attempts + 1. After 5 attempts an event becomes dead and alerts on-call.

A single-leader scheduler polls every 30 seconds, turns due timers into timer_fired inbox events (at most once per firing), and moves schedules to their next occurrence. The agent manages its own follow-ups with set_follow_up, cancel_follow_up and list_timers.

Column 2What a run works with

Worker

Workers form one shared pool. A worker that hears inbox_wake takes the client's lease with pg_try_advisory_lock(hash(client_id)), renewed every 30 seconds, so each inbox has at most one active worker.

while lease.held(client_id):
    events = claim_pending(client_id, limit=50)        # pending → claimed, where available_at <= now()
    if not events: break
    for session_id, group in group_by(events, "session_id"):
        session = (sessions.resume(session_id)          # compact first if over threshold
                   if session_id and sessions.resumable(session_id)
                   else sessions.create(client_id, kind_for(group)))
        outcome = run(session, group)                    # context → agent loop → write-back
        commit(outcome)                                  # transcript, memory, timers, outbox in one step
        check_acknowledged(group, outcome)               # must_acknowledge signals
        mark_done(group)
lease.release(client_id)
Events that arrive mid-run

They wait for the next run, which starts straight away. One exception: a client message arriving during a long signal run is added to the current session, so the client doesn't wait.

Crash safety

The transcript is saved after every tool round. Every order carries the idempotency key run_id:tool_use_id, which the credential proxy forwards to the broker, so a retried run can't place the same order twice.

Agent loop

A manual tool-use loop on the Messages API, so the permission gate can pause a run in the middle of a tool call. Request settings (illustrative; check against the SDK docs when implementing):

client.beta.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    thinking={"type": "adaptive"},
    output_config={
        "effort": EFFORT[run_type],                  # signal runs: "high" · chat, digest: "medium" · dreaming: "low"
        "task_budget": {"type": "tokens", "total": 64000},
    },
    betas=["compact-2026-01-12", "task-budgets-2026-03-13", "server-side-fallback-2026-07-01"],

    tools=TOOLS,
    system=SYSTEM_PROMPT,

).get_final_message()

Permissions

Every tool call goes through four stages. A blocked call goes back to the model as an error tool_result with the reason.

1 · Policy engine

The tool's tier, then argument rules: order size against limits, account ownership. It can only make a call stricter.

2 · Risk classifier

Screens classifier-tier calls and any call whose arguments came from untrusted text, such as a ticker first seen in a news item.

3 · Deferral manager

Writes a deferrals row, puts an approval card in the outbox, sets an expiry timer and pauses the session mid-call.

4 · Credential proxy

Adds the brokerage token from the vault and rejects any order without an approved, unexpired deferral ID.

CREATE TABLE deferrals (
  id            uuid        PRIMARY KEY,
  client_id     uuid        NOT NULL,
  session_id    uuid        NOT NULL,
  tool_use_id   text        NOT NULL,
  tool_name     text        NOT NULL,   -- 'place_order' | 'cancel_order'
  args          jsonb       NOT NULL,   -- exactly what the client sees and approves
  approver      text        NOT NULL,   -- 'client' | 'advisor'
  status        text        NOT NULL DEFAULT 'pending',  -- pending | approved | rejected | expired | executed
  expires_at    timestamptz NOT NULL,   -- end of the trading day
  decided_at    timestamptz,

);

On resume after an approval, the gate re-checks that the approval is valid and unexpired, the price hasn't moved beyond the allowed drift, and the arguments are byte-identical to what was approved. A rejection or expiry goes back to the model as the tool_result.

Scale, cost and observability

Parallelism
  • Each client's events run one at a time; clients run in parallel
  • The worker pool scales on inbox lag
  • A global Claude API limiter with three priority classes
  • A6 fan-out ordered by exposure, so the most exposed clients go first
Cost controls
  • Client params drop most signals before any run
  • Batching: severity 4–9 signals wait up to 15 minutes and share a run
  • Prompt caching on tools, system prompt and memory
  • Effort set per run type; dreaming through Batches
  • A daily token budget per client, with ops alerts
Metrics
  • Signals per detector, and the share dropped by the filter
  • Inbox lag p50/p99, dead events
  • Run duration, tokens, cost, cache hit rate
  • Messages per client per week, by kind
  • Approval rate and time to decide
Evals
  • Volume: replay a month of signals; too much, or missed?
  • Relevance: is the exposure reasoning right per holding?
  • Breaking event: replay a past sell-off
  • Injection red team with crafted news
  • Approval safety: no order without an approved deferral

Build vs. managed: the MVP hosts the agent loop and session store itself. Anthropic's Managed Agents (beta) could replace them; a short spike before building column 2 would settle it. Detectors, the inbox, the outbox, approval cards, compliance and the audit log stay ours either way.
